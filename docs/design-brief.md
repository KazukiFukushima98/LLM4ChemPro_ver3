# 研究環境の設計方針

Claude Code に基礎設計を依頼するための前提資料。

---

## 1. 目的

研究テーマ1つにつき1リポジトリとし、**計算・結果・論文・スライドを同一リポジトリで一元管理する**。

現状は Overleaf(論文)、ローカルの Python スクリプト(計算)、PowerPoint(スライド)が
分断されており、計算をやり直すたびに数値の転記・図の貼り直しが発生している。

達成したいのは次の一点に集約される。

> **パラメータを変えて再計算したら、`make` を叩くだけで論文とスライドの図・数値が更新される。**

副次的に、Claude Code が解析コード・結果データ・原稿を横断して読める状態になることを狙う。

---

## 2. 満たしたい要件

構成そのものではなく、**満たすべき性質**として定義する。
既存のディレクトリ構成のままこれらを満たせるなら、それが最良。

1. 重い計算とドキュメントのビルドが完全に分離されていること
   計算結果はファイル(CSV / Parquet)に落ち、原稿はそれを読むだけ。
   原稿を書いている間にソルバーが動くことは決してない
2. 作図処理が import 可能な関数として切り出され、論文とスライドから共用できること
   関数の引数は DataFrame、戻り値は Figure。関数内でファイル保存はしない
3. 入力データを書き換えないこと。読み取り専用の場所が明確であること
4. 計算の再現に必要な情報(commit hash / hostname / 時刻 / 設定)が結果と一緒に残ること
5. 環境が `uv` で再現できること。GPU 依存は optional に分離し、Mac では入らないこと
6. `make` で「必要な計算だけ」が走ること
7. **計算結果は run 単位で追記され、既存ファイルは上書きされないこと。**
   原稿は集約済みファイルを参照し、run が増えても原稿側の変更が不要であること
8. **投稿時点のデータを凍結する手段があること**

---

## 3. 使用ツール

| 用途 | ツール | 備考 |
|---|---|---|
| 原稿・スライド | Quarto (`.qmd`) | 英語のみ。日本語フォント設定は不要 |
| スライド出力 | reveal.js (HTML) | 単一ファイル埋め込みで配布 |
| 計算 | Python | |
| 環境管理 | uv | `pyproject.toml` + `uv.lock` |
| バージョン管理 | Git / GitHub | 結果データも追跡対象に含める |
| 文献管理 | Paperpile | `references.bib` を外部から自動同期 |
| 共著者との共有 | Overleaf(クラウド) | 移行しない。共有機能をそのまま使う |
| エディタ | VS Code + Quarto 拡張 | Remote-SSH でリモート計算機に接続 |
| 蓄積系メモ | Obsidian | リポジトリとは分離。読書メモ・着想用 |

## 4. データフロー

```
scripts/<計算>.py          重い計算。単独で実行し、結果をファイルに落とす
        ↓
results/runs/*.csv         1回の実行 = 1ファイル。追記のみ、上書き禁止
        + *.meta.json      commit hash / hostname / 時刻 / 設定
        ↓
scripts/aggregate.py       runs/ を結合
        ↓
results/aggregated/*.parquet
        ↓
        ├─→ paper/paper.qmd     作図関数を呼び、数値をインライン展開
        └─→ slides/*.qmd        同じ作図関数を呼ぶ
```

**作図関数は `src/` 側のモジュールに置き、`.qmd` はそれを呼ぶだけにする。**
論文とスライドで図が食い違う事故を構造的に防ぐため。
CSV からの作図は軽いので `.qmd` 内で実行してよい。
`#| label` と `#| fig-cap` を付けることで相互参照とキャプションが機能する。

## 5. 制約・前提

### 計算環境

- 複数マシン構成(MacBook / Linux 機 GPU 搭載 / Windows 機 GPU 搭載、Tailscale 接続)
- **Linux 機を計算ノードとして固定する**方針。MacBook からは Remote-SSH で接続
- GPU 依存パッケージは `optional-dependencies` の `cuda` に分離

> **本リポジトリでの例外**:計算(Aspen Plus COM)は Windows 機でしか動かないため、
> 計算ノードは Windows 機。Mac / Linux ではソルバー系依存(pywin32 / torch)は入らない。

### データの状態

- **データはまだ揃っておらず、今後も増え続ける。**
  「一度計算して終わり」を前提にした設計にしないこと
- 原稿執筆と計算追加が並行して進む

### 言語

- 論文・スライドは英語のみ
- 日本語を使うのは下書き段階のみ。`paper/draft-ja.md` として同一リポジトリに置く

### 結果データの扱い

- 数 MB 程度なら Git にコミットする。共著者が計算機を持たなくても原稿がビルドできる状態を保つ
- GB 規模になった場合のみ別途検討

## 6. 共著者との連携

Overleaf はクラウド版をそのまま使い、移行しない。自前ホストもしない。

- 本文のマスターは Overleaf 側に置く
- こちらからは**図表と生成された `.tex` のみ**を送る
- Quarto 側は `keep-tex: true` と `wrap: preserve` を設定する
  (`wrap: preserve` が無いと `.tex` の改行位置が毎回変わり、差分が読めなくなる)
- Overleaf での修正はダウンロードして差分を取り、`.qmd` に反映する

### 運用上の注意

Overleaf 公式は、Git からの push により変更履歴やコメントが失われる可能性があるため
Git の常用と track changes / コメントの併用を推奨していない。
したがって**常時同期ではなくラウンド制**とする。

1. 計算を確定し、図表を push する
2. 共著者へレビューを依頼する
3. **レビュー期間中は push しない**
4. コメントを回収し終えてから次の push

---

## 7. 投稿時の扱い

- ジャーナルには Quarto が生成した `.tex` と関連ファイルを提出する(Elsevier 系を想定)
- 図のファイル名は投稿要件に合わせる必要があるため、**所定の名前で出力する専用スクリプトを1本用意する**
  (`.qmd` のチャンクが自動生成する `fig-xxx-1.pdf` のような名前は使えない)
- 投稿直前に集約済みデータをスナップショットとして固定し、原稿はそれを参照するよう切り替える
  Git タグも打つ。これにより**投稿原稿は凍結され、研究は進み続けられる**

---

## 8. やらないこと(スコープ外)

- Overleaf の自前ホスト(共著者がアクセスできなくなるため)
- 論文本文を Quarto から全生成すること(共著論文では破綻する)
- Zotero の新規導入(Paperpile の GitHub 連携で足りる)
- 完全な脱 Microsoft(学会の書式要求などで `.docx` / `.pptx` が必要な場面は残る。
  最終出力だけ変換して対応する)
- Obsidian の内容をリポジトリに統合すること(蓄積系と出荷系は分離する)

---

## 9. 進め方

- **既存のディレクトリ構成を最大限尊重する。**「移動しない」を既定とし、
  移動を提案する場合は必ず理由と「移動しない場合の不都合」を述べること
- 既存の解析ロジックは書き換えない。移動と切り出しのみ
- 作業ブランチを切り、`main` に直接コミットしない
- 重い計算は実行しない。検証はダミーデータで `quarto render` が通ることの確認に留める
- 確定した構成と規約は `CLAUDE.md` に明文化する(理想形ではなく**実際の構成**を書く)
- 移行は1テーマのみで試し、詰まった箇所を潰してから他へ広げる
